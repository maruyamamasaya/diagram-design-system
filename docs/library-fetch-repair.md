# 資料取得の復旧と読取互換性

2026-10-20。発端は全資料取得不能と部分取得失敗。本人認証は200なのに一覧・lifecycleが409 INVALID_MANIFESTとなることを実測した。

## 原因

美術史 `e64e2471-56b8-4583-bc89-45e549053c22` v3の保存自体は成功していたが、本番読取コードは `slides/slide-NNN/slide.png` を認識せず、43,829,069 bytes PDF/30,136,175 bytes PPTXの資料限定承認も未配備だった。1件の検査失敗がcatalog走査全体を中断し、catalogを利用する資料状態APIも停止した。S3の帯域不足や本人ログイン失敗ではない。

Macには別途、旧版プロセスの重複起動、表紙が本文版枠を消費する旧キャッシュ制約があった。iOSのHTTP APIは401/429/5xxを回復せず終了していた。今回の全停止をこれらの推測で説明せず、上記の実HTTP応答で原因を特定した。

## 再発防止

- 保存とAPIで `src/library/presentation-contract.cjs` を共用。2種類のページパスを厳格に認識し、数値ページの連続性/重複、キー、サイズ、全承認ハッシュを確認する。
- `config/library-reader-contract.json` は共有検証器・旧metadata検査・サイズ検査・schemaのSHA256を固定する。Lambda包装時にソース不一致を拒否。承認台帳を含むfingerprintを `GET /v1/reader-contract` で公開する。ここにはアカウント・資料・認証値を返さない。資料APIの認証は維持する。
- 承認済み専用S3への実保存は旧/新両経路とも本番fingerprintとの完全一致が必須。欠落/不一致/通信不能ならS3のpreflightや公開ロック/PUTより前に停止する。dry-runはAWS通信なし。状態記録に確認したfingerprintを残す。
- 不正な完了manifestは、その版を一覧から隔離して `warnings:[{id,version,code}]` を返す。安全な他資料は継続表示。通信障害や権限不足を不正資料として握りつぶさない。両アプリは不正な版の件数を警告する。
- Swift共通の `LibraryArtifactPolicy` は資料限定大容量ファイルをID/版/名前/サイズ/SHA256へ束縛する。ルート回帰で承認台帳と両アプリの共通ポリシーが一致することを検査する。新しい限定承認を追加するときはAPIとアプリを先に対応・配布・実取得検証し、その後に公開する。

## 端末キャッシュと取得

閲覧コピーのディスク予算は両アプリ10,000,000,000 bytes（10進10GB）。メモリ画像キャッシュの容量ではない。キャッシュは開いた資料と表紙を対象とし、全資料・全形式の事前ダウンロードは行わない。

Macは既存Application Supportの利用者別copies領域を維持し、既定の30版本文件数枠を廃止。容量と利用順で版単位に整理し、取得中の版は保護する。アカウント別catalogも原子的に保存し、再起動時はネットワーク更新より先に一覧を復元する。

iOSは利用者別キャッシュをApplication Support/DiagramLibraryCacheへ移し、OSのCaches消去対象から外してバックアップから除外。旧Caches/DiagramLibraryがあれば移動して引き継ぐ。予算は利用者領域全体へ適用し、同一資料/版の詳細と本文を一緒に整理する。明示保存領域は別で、閲覧キャッシュの整理では消さない。資料の削除通知はキャッシュ保持より優先する。

取得済み詳細/本文は再照会を挟まず再利用。サイズ/SHA256不一致は表示を拒否する。APIの401は同じ本人で一度だけ更新。GETとURL発行の429/5xx/通信エラーは最大3回、Retry-Afterを尊重し30秒を超える指定はその場で再試行しない。S3の期限切れ・一時失敗も期限付きURLを取り直して限定再試行する。削除/移動などの書込操作を自動再送しない。既存の毎秒1要求/瞬間5要求は変更していない。

## 検証と配布

本人承認後に既存Lambdaコードのみを更新。新規リソース/IAM変更/予算変更なし。[承認内容と試算](library-fetch-repair-aws-proposal.md)。本番の一覧53資料/警告0と資料状態が200、未認証一覧401、最終コードSHA256とfingerprintを確認。

MacはApplications版を更新し、美術史v3/22ページの本文を目視。再起動後に同じ43.8MB PDFを表示し、ファイル更新日時不変とSHA256一致で再取得されていないことを確認。旧distプロセスは通常終了した。

Mira/Vesperaは既存本人ログインと実アプリの取得・保存コードを使った限定XCTestで、美術史22ページとリフキン1ページを本番API/S3から取得。サイズ/SHA256、PDFKitの描画、取得した同じファイルの通信なし再表示に合格。通常のRelease版は同じBundle ID/Teamで更新する。検証の一時領域だけを使用し、本人資料や整理情報を初期化していない。

詳細なコマンド/合否/配布版/証跡/残事項は[作業記録](../sessions/2026-10-20-library-fetch-stability.md)を正とする。全53資料の全形式を全端末で開いたという検証ではない。

## 資料とフォルダ所属の区別

S3の資料追加と整理情報のフォルダ所属は別。新規資料は既定で未整理となり、内容別の自動分類は実装していない。今回、直近5資料のMac割当がないことを読取確認した。取得修復を理由に本人のフォルダ所属を変更しない。
