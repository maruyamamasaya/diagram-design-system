# 整理同期：直近1時間5回と今回だけの追加

テスト本棚と127.0.0.1模擬サーバーで実装。普段の本棚/実機iPhone/AWSへは未適用。認証付きAWS実装は[未適用構成案](organization-sync-aws-plan.md)の次段階で行う。

## 利用者から見た動き

- 通常はMac/iPhoneを合算し、直近3600秒に同期の開始を5回まで許可する。時計の「毎時0分」でリセットせず、利用者のサーバー台帳で判定する。端末ごと5回ではない。
- 編集自体は上限中も保存でき、送信待ちに残る。前回確認時の合計/通常残りと、通常同期を再確認できる時刻を表示する。他端末の追加で時刻が変わることがあるため、最新判定はサーバーが行う。
- 通常枠がない場合、通常同期を押しても記録済みの待ち時間中はHTTPを送らない。回数表示の30秒更新は画面の時刻判定だけであり、サーバーをpollしない。
- 「今回の1回だけ追加で同期…」で確認ダイアログを出す。キャンセルなら追加しない。「今回だけ同期」で1セッションだけ追加する。追加分も直近1時間の合計へ含め、通常上限は5のまま。恒久解除の設定は設けない。追加するたびに新たな確認が必要。
- 初回取得とその確認後の送信は、有効な受付時間内なら同じ1回として扱う。受付は10分までなので、長く保留した初回確認は新しい枠を必要とすることがある。
- 切断/アプリ再起動/管理バックアップ復元でサーバーの台帳を消さない。ローカルにも次の時刻を残し、通常同期を勝手に再開しない。上限到達だけでは通常編集を止めない（初回レビュー中/通信中/復元待ちの編集停止は従来どおり）。

## 通信と追加許可

`SyncRateLedger`を利用者単位に1つ保持する。模擬サーバーは単一利用者・固定の1ライブラリで、別libraryIDは拒否する。実際のCognito subによる識別はまだ未実装であり、本番の利用者認可を検証済みとは扱わない。

1. beginで端末が永続化したattempt UUIDを予約する。同一UUIDの再送は同じ許可を返し、二重消費しない。失敗/期限切れで使い切らなかった予約も、開始から1時間は消費済みとして残す。
2. 5回到達後は拒否し、次の時刻とそのattempt専用のchallengeを返す。challengeは5分・1回の予約専用。アプリは確認を得た場合だけchallengeを送り直し、追加1回を受け取る。別attemptへの流用/期限切れ/内容を持たない解除要求は許可しない。確認画面は正規アプリの操作契約であり、サーバーが人の物理クリックを証明する仕組みではない。
3. 1受付は10分間、データ要求IDは最大12個。各IDの送信は初回を含め最大3回。HTTP再試行では同一の要求ID/操作ID/payloadを使い、短い待機+jitterを入れる。これを超える再試行や分割は次の同期へ残す。1回という表示を無限通信の許可にしない。
4. 正常終了でfinishし、同じ受付の使い回しを止める。終了通信に失敗してもローカルの受付は破棄し、サーバーでは10分/データ要求上限を維持する。受付/終了のHTTP再試行も各呼出3回まで。

SyncLabSessionのsync-throttle.jsonへ予約ID/許可/次の時刻/接続先/ライブラリIDを原子的に保存する。壊れた台帳を切断操作で初期化しない。ソースの管理JSON/バックアップにこの台帳を混ぜず、管理データ復元後も制限を維持する。ローカルキャッシュの時計やファイルが改変されても、本番はサーバー側の時刻/認証済み利用者台帳で判定する。

模擬serverはHTTPロックの下で台帳/同期状態を保存する。begin/sync/finishは同じ永続ファイルに入り、HTTPごとにSwiftプロセスを再生成しても制限を保持する。許可のないデータ要求を拒否し、上限なしの旧/syncへは到達できない。AWS実装は同じ管理オブジェクト内の台帳と状態をS3の条件付き書込で直列化する。複数Lambdaでのメモリカウンターは使わない。台帳だけの更新は資料整理のrevisionを増やさず、S3 ETagによる排他と整理項目のrevisionを分ける。

```sh
CLANG_MODULE_CACHE_PATH="$PWD/mac-app/.build/clang-cache" \

```

## 確認範囲と費用

共通28/Mac26/iOS64。単体は移動窓の境界・予約再送・追加challengeの期限/使い回し・要求/再試行/受付期限・破損台帳の保護。実HTTPは2端末合計5回、6回目拒否、ACK喪失、送信待ち/再起動/切断後の制限維持、追加1回、10並行要求のうち5件だけ許可を確認。HTTP要求数も数え、待ち中の再試行/再起動が余分な通信を発生させないことを照合した。

専用ツールで、Macの上限/待ち時刻/キャンセル/追加1回/通常上限維持と、上限中の通常フォルダ編集→送信待ち1件を確認。iOSも同じサーバーの上限を取得し、確認した追加1回の初回統合を完了。従来の管理データ復元ダイアログも表示/キャンセルを確認した。実データ/Applications版/実機iPhone/AWS変更なし。[証跡](../sessions/2026-10-18-sync-quota.md)。

この制限は費用の厳密な上限ではない。5回は論理同期の開始数であり、1回が複数HTTP/操作/転送を伴う。通常成功でもbegin+データ+finishで少なくとも3要求、初回/分割/再試行/追加同意の往復はさらに増える。拒否された要求にもAPI等の費用が発生し得る。[2026-10-18再試算](organization-sync-aws-plan.md)では台帳書込/制御要求/再試行/転送量を計上した。正常利用の100円以内の見込みと、再送/分割/追加で超えるケースを区別する。AWS適用前には実測と最新単価で再確認する。今回のローカル実装のためAWSの変更や課金API照会は行っていない。
