## 境界とデータ

既存の[整理モデル](library-organization.md)から明示的に変換する。資料IDを不透明な文字列として扱い、タイトル・パス・端末時計では照合しない。UUIDの大小文字など出所間の対応は呼出側のdocumentID変換で明示する。まとめのMember内IDもアダプターで同じ対応へ変換してから渡す。異なるIDを同じIDへ変換し情報が衝突する場合は変換を拒否する。

サーバー/クライアントはlibraryIDで分離。これはローカルテストの領域識別であり、認証や本人確認の代替ではない。MemberはCodable/Equatable/Sendableのアダプター所有スナップショットで、実アプリ接続時は既存のURLを持たないBookReference/CloudDiagramに相当する形式を使う。Member固有の種別/形式/ID検証はアダプターが担当し、サーバーにはmemberID関数を渡して重複を検査する。

送信するキー：

|キー|値・競合単位|
|---|---|
|folder/UUID|フォルダ名・親。編集はフォルダ単位|
|assignment/資料IDの符号化|所属フォルダ。deletedで未整理へ戻す|
|group/資料IDの符号化|仕事/私用/その他|
|tag/資料IDの符号化/正規化タグの符号化|1タグずつ追加/削除|
|collection/UUID|まとめの名前・順序付きMember。まとめ単位で競合|
|folder-order|フォルダUUID列。並べ替え全体で競合|

資料IDとタグの符号化は可逆のURL-safe Base64。タイトル/名前で同一視しない。投影時にフォルダのiconFileを除き、資料本体・Macパス/bookmark・画像本体・認証・キャッシュ・端末の非表示は送信しない。受信結果を既存設定へ適用するとき、端末固有アイコン/保存場所などを消さずUUIDで再結合する責務はアプリアダプターに残す。

## 変更・再送・保存

SyncOperationはUUIDの操作ID、キー、読込済みの項目revision、新しい値。クライアントはbaseline、pending、conflictsをCodableで保持し、save/loadで原子的保存できる。呼出側は編集直後/送信前にチェックポイントを保存し、同期成功後も失敗時も更新状態を保存する。値型のため呼出側で編集/同期/保存を直列化する必要がある。今回、既存Mac/iOS Storeへこのライフサイクルを自動接続してはいない。

オフラインではpendingを積み、同じキーの未確定編集は最新の意図にまとめる。送信前に親フォルダを先に並べ、1要求500操作ずつ処理する。サーバーは操作IDと内容・結果を永続化し、同一ID/同一内容の再送には既存結果を返す。同一IDで異なる内容は要求処理前に拒否する。サーバー書込後に応答が消えても、再送でrevisionを重ねて増やさない。途中で失敗しても未確認の操作はpendingに残る。

応答に全操作の対応するreceiptが揃わない、領域が違う、サーバーrevisionが逆行する場合はキューを消さない。サーバー状態の保存とreceipt保存は同じJSONの一回の原子的書込。ローカルHTTPブリッジはプロセス内ロックで読込→Swift処理→書込を直列化し、保存後に応答する。本番の複数サーバー間の排他や耐久性を検証したものではない。

## 同時編集と削除

別キーの操作は統合。別々のタグ追加は両方残す。同じ資料の移動、同じフォルダの編集、同じまとめの名前/順番、同じフォルダ順の変更は、読込revisionと現行revisionが違えば競合。端末時計や後着順で上書きしない。既に同じ値なら成功扱い。独立した他の操作は競合中も処理する。

競合にはローカル提案とサーバー側の値を保持し、ディスク保存/再起動で失わない。resolveでサーバー側を採用するか、現在のbaselineを基に新しい操作IDでローカル提案を再送できる。ただし削除済みフォルダ/まとめは元のUUIDで再作成できない。復帰したい場合は新規UUIDを作り明示的に移し替える。矛盾した入力もinvalidとして提案を保持し、勝手に破棄しない。

フォルダ/まとめの削除はtombstone（削除済み記録）を残し、ローカル模擬版では期限を設けず保持する。親フォルダ削除は、そのサーバー処理時点の子孫と所属資料を原子的に未整理へ戻し、順序から削除する。グループ/タグ/まとめ内容と資料本体は変えない。古い端末から子フォルダの名前変更/削除先への移動が届いても復活させずinvalidに残す。競合提案は通常の受信状態へ重ねず、削除済みのものを見かけ上復活させない。

タグ削除はタグキーのdeleted。既に同期開始したタグへの古い追加/削除はrevisionで判定する。初回統合では過去に「消した」のか「元からない」のか分からないため、タグの不存在を削除とは推測せず和集合にする。

## 既存データの初回統合

1. 呼出側がローカルバックアップを作り、利用者/出所/資料ID対応を確認する。今回の検証は合成データのみで実端末から読まない。
2. 各端末を別々にimporting/loadで読む。Macのlibrary.jsonに後から追加した分類/まとめも保持。iOSはorganization.jsonと既存classifications/collectionsを呼出側で組み立てる。
3. 各端末の状態をProjection.recordsへ変換する。原本設定とまとめの順番/ID/スナップショットは書き換えない。フォルダ画像名は転送しない。
4. OrganizationImportPlanで統合。異なるフォルダUUIDは同名でも別物。別のタグは和集合。同じ資料の所属/分類・同じUUIDのフォルダ/まとめ・異なる手動順序は両案を提示する。
5. 競合が全て解決されるまでenqueueは拒否。循環/親不足はキューを一部変更せず拒否する。通常の全状態置換は行わない。
6. 確認後に親から順に操作へ変換して送信する。同じ計画を再適用しても、同じ値は追記しない。再送は操作IDで重複しない。既にサーバーにtombstoneがある場合、旧端末の初回取込でも自動復活はしない。

旧importingに複数の入力ファイルを渡して同一IDの異なる分類/同一UUIDの異なるまとめが見つかった場合も、上書きせずconflictingImportを返す。端末間のレビューはImportPlanへ分ける。

## 実行と検証

リポジトリのルートから実行：

```sh
CLANG_MODULE_CACHE_PATH="$PWD/mac-app/.build/clang-cache" \
  swift test --disable-sandbox --package-path packages/LibraryOrganization \
  --cache-path "$PWD/mac-app/.build/cache"
python3 scripts/organization-sync-http-check.py \
  packages/LibraryOrganization/.build/debug/OrganizationSyncMock
```

HTTP検証ハーネスはPython標準ライブラリだけを使い、127.0.0.1の空きポートと一時ディレクトリで起動する。HTTPの各要求をSwiftの模擬サーバーに渡し、同期処理をPython側へ複製しない。検証後はサーバーを停止し一時データを削除。Swift HTTPTransportもhttp://127.0.0.1のみ許可し、リダイレクトを拒否する。テスト用で認証はなく、LAN/外部への公開は禁止。

CLIのMember=Stringは合成テスト専用。実アプリの資料取得やクラウドへ接続しない。実際のHTTPでフォルダ/所属の送受信、書込後の応答喪失と再送、2クライアントのタグ統合を確認する。単体テストでは競合/解決/削除/初回統合/再起動/不完全応答/500件超のオフラインキューも確認する。
