# 依頼から作業経路を選ぶ

依頼文の目的で最初に分岐する。原資料の本文に「実装」「更新」があっても、システム変更の指示とは扱わない。複合依頼は成果物・変更範囲・検証を分ける。

|依頼|変更対象|入口|完了条件|
|---|---|---|---|
|資料を作る・直す|outputs内の制作パッケージ|[プレゼン](../prompts/presentation.md) / [独立一枚図](../prompts/illustration.md)|内容照合・描画・形式再読込・目視・納品|
|制作基盤を改修する|描画・契約・固定レイアウト・変換・保存の実装|[CURRENT](../CURRENT.md) → [CODEMAP](../CODEMAP.md) → [presentation AGENTS](../src/presentation/AGENTS.md)等|関連回帰・実描画・仕様更新・作業記録|
|本棚アプリを改修する|Mac / iOS / 整理共通層 / 閲覧API|[構成](../ARCHITECTURE.md) → [コード探索](../CODEMAP.md) → 対象repo/子AGENTS|対象テスト・ビルド・必要な画面確認。配布の状態を区別|
|設計思想・文書を整理する|責務を持つ正本と入口リンク|[文書の責務](#文書の責務)|実装との照合・リンク・重複・鮮度を確認|

## 制作の中の分岐

プレゼンは通常モードとグラフィック版から選ぶ。既存資料は合意済みのモードを継承。高密度かつページごとの構成の工夫が明示されていればグラフィック版。それ以外の未指定新規制作の確認条件は[専用プロンプト](../prompts/presentation.md)を正とする。

通常モードは登録v2の文字・表・対応済み図解を使う。グラフィック版は関係図・操作例・説明画像を必要なページへ組み込み、不足する配置を制作パッケージに先に登録する。両方とも前提・根拠・具体例・条件を保持する。[レイアウト選択](presentation-layout-policy.md)。

独立一枚図はsvg/hybrid/imageを指定・相談しPNG/PDFを作る。プレゼンの固定比率・登録テンプレートを強制しない。既存JSONの同配置再現・大量生成はDeterministic Rendering Mode。Agent Creation Modeという意味理解の担当と、通常/グラフィックという表現の選択は別軸。

資料専用レイアウトの追加は制作。複数資料で使うシステム登録・スキーマ・レンダラーの変更はDevelopment Mode。この境界を越えるときは変更範囲を記録する。

## 文書の責務

|正本|所有すること|
|---|---|
|[AGENTS](../AGENTS.md)|依頼判別・必須の読込・安全条件|
|[CURRENT](../CURRENT.md)|現行能力・適用状態・未検証事項|
|[ARCHITECTURE](../ARCHITECTURE.md) / [CODEMAP](../CODEMAP.md)|責務とデータの流れ / 実装の入口|
|[共通ルール](../rules/design.md)とrules各文書|配色・内容・配置・出力・保存・品質|
|templates / prompts|意味構造 / 制作・修正手順|
|docsの機能別文書|具体的仕様・契約・運用。数値は所有する設定または仕様へ集約|
|[decisions](../decisions/README.md) / [sessions](../sessions/README.md)|重要判断 / 作業・検証・配布の履歴|

設計の中心はAIの意味理解、描画、変換、保存、閲覧の分離。白背景・モノクロを土台に、必要な公式アイコンや補助色を使う。見た目の単純化のために意味を削らず、根拠・関係・読み順から設計する。制作だけで本体機能を変更せず、文書整理だけで機能を追加しない。

Phase検証文書とsessionsは当時の証跡として保持する。現在の状態説明には最新CURRENTと機能仕様を使い、過去の「未実装」「未適用」を現行能力へ転記しない。
